# Техническое задание

## Учебный проект: интернет-магазин на Vue 3

Срок выполнения: 4 недели.

## 1. Назначение проекта

Необходимо разработать frontend-приложение (SPA) для небольшого интернет-магазина.

Приложение должно позволять пользователям просматривать каталог товаров, добавлять товары в корзину, оформлять заказы и отслеживать их статусы. Менеджеры магазина должны иметь возможность управлять товарами, остатками и заказами.

Проект выполняется полностью на Vue. Роль backend выполняет mock REST API на json-server, который входит в состав репозитория и запускается одной командой. Отдельный «настоящий» backend писать не нужно.

## 2. Цели проекта

В ходе выполнения проекта ученик должен показать умение:

- проектировать SPA на Vue 3 с Composition API;
- использовать TypeScript в компонентах, сторах и API-слое;
- организовывать состояние приложения в Pinia;
- настраивать маршрутизацию и защиту страниц через Vue Router;
- работать с REST API и JWT-авторизацией через axios;
- реализовывать формы с валидацией;
- выносить переиспользуемую логику в композаблы;
- реализовывать бизнес-логику корзины, заказов и остатков;
- писать тесты для компонентов, сторов и композаблов;
- оформлять проект для демонстрации и проверки.

## 3. Технологический стек

Frontend:

- Vue 3 (Composition API, `<script setup>`);
- TypeScript;
- Vite;
- Vue Router;
- Pinia;
- Axios;

- Vitest и Vue Test Utils;
- ESLint и Prettier.

Mock API:

- json-server версии 0.17.x;
- json-server-auth;
- concurrently — для запуска frontend и mock API одной командой.

Инфраструктура:

- GitHub Actions.

## 4. Роли пользователей

В приложении должны быть реализованы роли:

- `USER` - покупатель;
- `MANAGER` - менеджер магазина.

Права доступа:

- `USER` может просматривать каталог, работать с корзиной, оформлять заказы, просматривать свои заказы и уведомления;
- `MANAGER` может управлять товарами, категориями, остатками и статусами заказов.

Проверка ролей выполняется на frontend: в navigation guards и при отображении элементов интерфейса.

Это учебное упрощение. В реальном проекте права всегда проверяются на backend. Ученик должен понимать это ограничение и уметь объяснить его на собеседовании.

## 5. Функциональные требования

### 5.1 Регистрация и авторизация

Должны быть реализованы:

- регистрация пользователя по email и паролю;
- вход пользователя по email и паролю;
- хранение JWT access token и данных текущего пользователя в Pinia;
- восстановление сессии после перезагрузки страницы;
- axios-интерцептор, добавляющий токен в заголовок `Authorization`;
- обработка ответа 401: сброс сессии и редирект на страницу входа;
- просмотр и редактирование профиля текущего пользователя;
- выход пользователя;
- защита приватных страниц через navigation guards;
- редирект авторизованного пользователя со страниц входа и регистрации.

Профиль пользователя должен содержать:

- email;
- имя;
- фамилию;
- телефон;
- роль;
- дату регистрации.

Токен допускается хранить в `localStorage`. Ученик должен уметь объяснить риски такого хранения (XSS) и назвать альтернативы (httpOnly cookie).

### 5.2 Каталог товаров

Должны быть реализованы:

- список товаров с пагинацией;
- страница товара;
- категории товаров;
- поиск по названию и описанию с debounce;
- фильтрация по категории;
- фильтрация по цене;
- фильтрация по наличию товара;
- сортировка по цене;
- сортировка по дате добавления;
- хранение состояния поиска, фильтров, сортировки и страницы в query-параметрах URL: при перезагрузке страницы и при переходе по скопированной ссылке состояние каталога должно восстанавливаться;
- создание товара менеджером;
- редактирование товара менеджером;
- удаление товара менеджером;
- публикация и скрытие товара.

Поля товара:

- название;
- описание;
- категория;
- цена;
- количество на складе;
- статус публикации;
- URL изображения;
- дата создания;
- дата обновления.

Покупатели должны видеть только опубликованные товары.

### 5.3 Корзина

Должны быть реализованы:

- отдельный Pinia store корзины;
- добавление товара в корзину;
- изменение количества товара в корзине;
- удаление товара из корзины;
- очистка корзины;
- расчет итоговой суммы через computed;
- запрет добавления количества, превышающего остаток на складе;
- счетчик товаров в корзине в шапке приложения;
- сохранение корзины после перезагрузки страницы.

Корзина хранится в `localStorage`: через `pinia-plugin-persistedstate` или вручную через `watch`.

### 5.4 Заказы

Должны быть реализованы:

- оформление заказа из корзины;
- проверка актуальных остатков запросом к API перед созданием заказа;
- уменьшение остатка товара после успешного создания заказа;
- сохранение в заказе названия и цены товара на момент покупки;
- просмотр пользователем списка своих заказов;
- просмотр пользователем деталей своего заказа;
- просмотр менеджером всех заказов;
- изменение статуса заказа менеджером;
- отмена заказа пользователем;
- возврат товара на склад при отмене заказа.

Пользователь не может оформить заказ, если запрошенное количество товара превышает доступный остаток.

Проверка и изменение остатков выполняются на клиенте последовательными запросами к mock API. Это учебное упрощение: в реальном проекте эта логика выполняется на backend в транзакции. Ученик должен уметь объяснить, почему.

### 5.5 Статусы заказа

Заказ должен поддерживать статусы:

- `NEW` - заказ создан;
- `PAID` - заказ оплачен;
- `PROCESSING` - заказ обрабатывается;
- `SHIPPED` - заказ отправлен;
- `COMPLETED` - заказ завершен;
- `CANCELLED` - заказ отменен.

Переходы статусов:

- пользователь создает заказ в статусе `NEW`;
- пользователь может перевести заказ из `NEW` в `PAID` кнопкой "Оплатить";
- менеджер может перевести заказ в `PROCESSING`, `SHIPPED` или `COMPLETED`;
- пользователь может отменить заказ, если он находится в статусе `NEW` или `PAID`;
- отмененный или завершенный заказ нельзя изменить.

Допустимые переходы должны проверяться в коде, а недоступные действия - скрываться в интерфейсе.

Реальное подключение платежной системы не требуется.

### 5.6 Уведомления

Должны быть реализованы:

- создание уведомления при создании заказа;
- создание уведомления при изменении статуса заказа;
- список уведомлений пользователя;
- отметка уведомления как прочитанного;
- счетчик непрочитанных уведомлений в шапке приложения.

Уведомление должно содержать:

- пользователя;
- текст;
- статус прочтения;
- дату создания.

Уведомления создаются клиентом через POST-запрос к mock API в момент события.

## 7. Модель данных

В `db.json` mock API должны быть реализованы сущности:

- `users`;
- `categories`;
- `products`;
- `orders`;
- `notifications`.

Позиции заказа хранятся массивом внутри заказа:

```json
{
  "orders": [
    {
      "id": 1,
      "userId": 2,
      "status": "NEW",
      "items": [
        { "productId": 5, "title": "Клавиатура", "price": 2990, "quantity": 2 }
      ],
      "totalAmount": 5980,
      "createdAt": "2026-09-01T10:00:00.000Z",
      "updatedAt": "2026-09-01T10:00:00.000Z"
    }
  ]
}
```

Требования к данным:

- заказ принадлежит одному пользователю;
- заказ содержит одну или несколько позиций;
- позиция заказа хранит id товара, название, цену на момент покупки и количество;
- изменение цены товара не влияет на уже созданные заказы;
- удаление товара не должно ломать историю заказов;
- остатки товара не могут становиться отрицательными.

## 8. REST API (mock)

### 8.1 Авторизация и пользователь

- `POST /register` - регистрация (json-server-auth);
- `POST /login` - вход, возвращает `accessToken` и данные пользователя;
- `GET /users/{id}` - данные пользователя;
- `PATCH /users/{id}` - обновление профиля.

### 8.2 Категории и товары

- `GET /categories` - список категорий;
- `POST /categories` - создание категории;
- `GET /products` - список товаров с параметрами:
  - `q` - поиск;
  - `categoryId` - фильтр по категории;
  - `price_gte`, `price_lte` - фильтр по цене;
  - `isPublished` - фильтр по статусу публикации;
  - `_sort`, `_order` - сортировка;
  - `_page`, `_limit` - пагинация (общее количество - в заголовке `X-Total-Count`);
- `GET /products/{id}` - детали товара;
- `POST /products` - создание товара;
- `PATCH /products/{id}` - редактирование товара;
- `DELETE /products/{id}` - удаление товара.

### 8.3 Заказы

- `GET /orders?userId={id}` - заказы пользователя;
- `GET /orders` - все заказы (для менеджера);
- `POST /orders` - создание заказа;
- `GET /orders/{id}` - детали заказа;
- `PATCH /orders/{id}` - изменение статуса заказа (оплата, отмена, статусы менеджера).

### 8.4 Уведомления

- `GET /notifications?userId={id}&_sort=createdAt&_order=desc` - уведомления пользователя;
- `POST /notifications` - создание уведомления;
- `PATCH /notifications/{id}` - отметка прочитанным.

Ресурсы `orders` и `notifications` должны быть закрыты от неавторизованных запросов средствами json-server-auth (guarded routes).

## 9. Требования к mock API

Mock API должен:

- находиться в отдельной папке `mock/` внутри репозитория;
- использовать фиксированные версии `json-server@0.17.x` и `json-server-auth`;
- запускаться отдельным npm-скриптом;
- содержать `db.json` с demo data: категории, не менее 20 товаров, тестовые пользователи обеих ролей, несколько заказов и уведомлений;
- иметь инструкцию по запуску в README.

## 10. Требования к frontend

Frontend должен:

- использовать Vue 3, Composition API и `<script setup>` во всех компонентах;
- использовать TypeScript: типизированные props, emits, сторы и ответы API;
- использовать Pinia для состояния: минимум сторы auth, cart и notifications;
- иметь маршрутизацию с lazy loading страниц через динамический import;
- использовать navigation guards для проверки авторизации и роли;
- иметь отдельный API-слой на axios с интерцепторами;
- содержать минимум три композабла (например: `useDebounce` для поиска, `usePagination`, `useToasts`);
- содержать минимум одну кастомную директиву (например, `v-click-outside` для выпадающего меню);
- использовать `Teleport` для модальных окон;
- использовать `Transition` и `TransitionGroup` (например, для toast-сообщений об успехе и ошибках операций);
- валидировать формы через VeeValidate со схемами Zod или Yup;
- отображать ошибки API пользователю;
- не мутировать props, использовать ключи в `v-for`, использовать computed вместо дублирования вычислений в шаблонах;
- показывать разные элементы интерфейса для разных ролей.

Должны быть покрыты тестами (Vitest, Vue Test Utils):

- cart store: добавление товара, повторное добавление того же товара, изменение количества, удаление, расчет суммы, запрет превышения остатка;
- auth store: вход сохраняет токен и пользователя, выход очищает состояние;
- минимум один композабл;
- компонент формы входа: отображение ошибок валидации, отправка корректных данных;
- компонент карточки товара: отображение данных, событие добавления в корзину;
- navigation guard: редирект неавторизованного пользователя с приватной страницы.
